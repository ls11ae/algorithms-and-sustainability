## Build

Tested with Decker 0.15.0-rc2 (Linux).

```
decker html                                         # build everything into public/
decker public/lectures/01-introduction-deck.html    # build only lecture 1
decker public/notes/01-introduction-page.html       # build only chapter 1 of the notes
decker --server                                     # preview with live reload
```

`public/` is the build output; it does not need to be kept or shared.

To regenerate the figures (needs matplotlib, numpy, scipy; Lato via `LATO_DIR`):

```
LATO_DIR=/path/to/lato/fonts python3 tools/make_figures.py lectures/figures
LATO_DIR=/path/to/lato/fonts python3 tools/make_clustering_figures.py ../movement-analysis/data lectures/figures
LATO_DIR=/path/to/lato/fonts python3 tools/make_segmentation_figures.py ../movement-analysis/data lectures/figures
```

## Colors on the slides

`static/aus.css` gives colors a fixed meaning, built from the theme's accent colors:

| Color | Meaning | In Markdown |
|-------|---------|-------------|
| blue | emphasis: key terms, information and example boxes | `**bold**`, `## Title {.info}` |
| orange | questions to the audience, activities, quizzes | `## Title {.ask}`, `[text]{.ask}` |
| green | structure and links: title bars, section slides, links | theme |
| red | caution, common misconceptions (rarely) | `## Title {.warn}`, `[text]{.warn}` |
| grey | secondary information: sources, references | `[text]{.source}` |

The SDG colors appear only in the SDG chips (`[7]{.sdg .s7}`).

## Publishing

The workflow `.github/workflows/publish.yml` builds the site on every push to GitHub and
publishes it on GitHub Pages. It runs `decker html` and `decker pdf` and copies
`notes/*.pdf`. A local build is not needed; `decker pdf` does not run on Windows anyway.

One-time setup:

1. Save the workflow file as `.github/workflows/publish.yml` in this folder (in VS Code:
   *New File* and type this path).
2. On GitHub, create an empty public repository: *New repository*, choose the *Owner* (your
   account or an organization such as `ls11ae`), and add no README, `.gitignore` or licence.
   VS Code's *Publish to GitHub* always creates the repository in your own account, so it
   does not work for an organization.
3. Push this folder to the repository. Open this folder itself in VS Code, not a parent
   folder. Then *Source Control → Initialize Repository*, commit all files, *⋯ → Remote →
   Add Remote…* with the repository URL and the name `origin`, and *Publish Branch*.
   On the command line:

   ```
   git init -b main
   git add .
   git commit -m "Lecture 1"
   git remote add origin https://github.com/<owner>/<repository>.git
   git push -u origin main
   ```

4. In the repository, go to *Settings → Pages → Build and deployment* and set *Source* to
   **GitHub Actions**.
5. Start the workflow once by hand: *Actions → Publish slides → Run workflow*. The run that
   started with the first push fails because Pages was not enabled yet.
6. After about two minutes the site is at `https://<owner>.github.io/<repository>/`. Put this
   link in Moodle.

After that, every push updates the site. When you add a lecture, add a row to `index.md`.

The repository and the site are public, including the speaker notes. Keep solutions, exam
material and guest slides out of it and put them on Moodle.

### What goes where

- **GitHub (public):** slides and lecture notes, each as web version and PDF, one row per
  lecture on the landing page.
- **Moodle (course members):** the slide PDF and the recording (MP4) of each lecture, each with
  a link to the lecture on GitHub, plus announcements, exercises, quizzes and the forum.

### Lecture recordings

Decker's recordings (`*-recording.webm`, `*-recording.mp4`) go to Moodle, not into this
repository; `.gitignore` excludes them. `decker crunch` turns the recording into an MP4.

If you ever want the player that links video and slides on the public site: it also works
when the MP4 is on another web server. Upload it there and add this to the front matter of
the deck:

```yaml
explain:
  video: https://server.example/aus/01-introduction-recording.mp4
```

`*-times.json` (the slide timings) and captions (`*.vtt`) stay next to the deck in the
repository. The video server must

- serve the file without login,
- send the header `Access-Control-Allow-Origin: *`; for Apache, put this line in the
  folder's `.htaccess`: `Header set Access-Control-Allow-Origin "*"`,
- support range requests (Apache and nginx do).

YouTube does not work, because the player needs a direct link to the MP4 file.

Alternative without GitHub: add this to `decker.yaml` and run `decker publish`. It needs rsync
and ssh, so on Windows it needs WSL.

```yaml
publish:
  rsync:
    destination: user@server:/path/to/web/aus/
```

`decker publish` deletes files in the destination folder that are not in `public/`, so use a
folder of its own.
